# Building a component

## Where it goes

- `components/ui/` — shadcn primitives. **Generated by the CLI; don't hand-write files here.** Editing them is fine once they exist.
- `app/components/` — components specific to this app (`Navbar`, `ProductCard`) that compose the primitives above.

Import through the `@/` alias, which maps to the repo root: `@/components/ui/button`, `@/lib/utils`.

## Get primitives from the CLI

If you need a primitive that isn't in `components/ui/` yet — dialog, select, sheet, badge — install it:

```bash
npx shadcn@latest add dialog
```

This matters more than it looks. `components.json` pins this project to the `radix-nova` style with a `neutral` base color, and the CLI generates components matching that config. A hand-written "dialog" won't match the existing components' variants, focus rings, or dark-mode behavior, and the mismatch is tedious to unpick later. Check `components/ui/` first, then install.

## Style with theme tokens, not raw colors

`app/globals.css` defines the palette as CSS variables with light and dark values. Use the semantic Tailwind classes that read them:

| Use | Not |
|---|---|
| `bg-background`, `text-foreground` | `bg-white`, `text-black` |
| `text-muted-foreground` | `text-gray-500` |
| `bg-primary`, `text-primary-foreground` | `bg-neutral-900` |
| `border-border` | `border-gray-200` |
| `bg-destructive` | `bg-red-600` |

Hardcoded colors look right in light mode and break in dark mode, because they don't participate in the `.dark` overrides. Tokens adapt for free.

## Compose classes with `cn()`

When a component takes a `className` or toggles classes conditionally, merge through `cn()` from `@/lib/utils` (clsx + tailwind-merge):

```tsx
import { cn } from "@/lib/utils";

<div className={cn("rounded-lg p-4", isActive && "bg-accent", className)} />
```

Plain string interpolation leaves conflicting Tailwind classes both present, and which one wins comes down to CSS source order rather than your intent. `cn()` resolves the conflict so a caller's `className` can actually override the default.

## Type the props

Give every component a real prop type. `any` disables the type checker exactly where mistakes are most likely, and it's a lint **error** in this repo — it will fail `npm run lint`.

Put shared shapes in one place so the type doesn't drift between the card, the cart, and the admin table:

```tsx
export type Product = {
  id: number;
  name: string;
  price: number;
  description: string;
  image: string;
};

export default function ProductCard({ product }: { product: Product }) {
  // ...
}
```

## Images

Use `next/image`, not `<img>`. It serves modern formats, sizes images for the device, and prevents layout shift as they load — worth it here because product photos and the hero are the heaviest things on the page.

```tsx
import Image from "next/image";

<Image src="/painting.jpg" alt="Abstract painting in blues and golds" width={400} height={300} />
```

Two rules that come up constantly:

- **`alt` is required.** Describe the image for someone who can't see it. For purely decorative images pass `alt=""` — deliberately empty, so screen readers skip it.
- **Add `priority` to the largest image above the fold** (the hero on the home page). It's the one the browser should not lazy-load, since it's what the page's load speed is measured on.

For an image that fills a sized container, use `fill` with `object-cover` and give the parent `relative`.

## Headings describe structure, not size

Use one `<h1>` per page — the page's actual title. Inside a card, the product name is an `<h2>` or `<h3>`; price and description are `<p>` or `<span>`.

Screen reader users navigate by jumping between headings, so a card with three `<h1>`s makes the page's outline unusable. If you want a heading to look smaller, style it (`text-sm`) rather than demoting the tag.

## Forms

Tie every `Label` to its input with matching `htmlFor` and `id`:

```tsx
<Label htmlFor="email">Email</Label>
<Input id="email" type="email" required />
```

Without the pair, clicking the label doesn't focus the field and screen readers announce the input unlabeled. The visual proximity is not enough.

A `<form>` also needs somewhere to go — an `action` or an `onSubmit`. A form that silently does nothing on Enter reads as a broken page.
